\section{Results}

\textbf{Strengths.} The full \texttt{pytest} run passed (247 tests). The distribution is intentionally skewed toward unit tests (239/247, about 97\%), which provides dense checks for local logic (KB transforms, engine transitions, resilience updates, and payoff helpers). The remaining integration tests (8/247, about 3\%) focus on cross-module contracts where regressions are most likely to break end-to-end behavior.

\textbf{Weaknesses.} README filenames still diverge from the tree in places. Tests use hand-built fixtures, not external datasets. We did not run large hyperparameter sweeps or formal UI user studies. As a result, the strongest claim supported here is implementation reliability for tested paths, not statistical superiority of one strategy family over another.

Table~\ref{tab:pytest} lists collection counts by area; every listed test passed in the aggregate run reported above. Practically, this means the module interfaces used by analysis and UI layers are stable on the evaluated snapshot, so interpretation in later sections rests on reproducible software behavior rather than one-off manual runs.

Reading Table~\ref{tab:pytest} together with the passing full-suite run supports two narrow claims: first, the low-level pieces (KB, engine, Nash helpers, repeated analysis, RL smoke) each have direct tests; second, a small but targeted set of integration tests guards the interfaces where regressions hurt most. In combination with Figure~\ref{fig:qlheat}, the results support a ``working analytics stack'' conclusion: logic, simulation, equilibrium analysis, and learning artifacts can be generated consistently from one codebase. It does \emph{not} support a claim that every feature in the Streamlit UI is exhaustively clicked in CI---only that the underlying Python contracts those screens rely on are exercised.
